## 3. What v0.4-beta changed for the fork

CLAUDE.md carries the standing version of this. In short:

- **Gravity is the only executor.** The row executor, `sqe` and `pgrcolumnar2` are gone. A plan Gravity can't run fails with `gravity: refused (...)`. As shipped it refused both vector AMs: an `ORDER BY` over a vector index and any INSERT into a table with one. The fork adds `Hnsw` and `Ivfflat` to Gravity's `IndexAm`, maps them in `am_of`, admits them in `write_index_am::insertable`, keeps them out of `index_opc`'s builtin-handler premise, and registers IVFFlat's three GUC thread-locals for pool workers. The fork's whole change under `crates/gravity/` is 8 files, 26 lines added. **Recheck these sites after every upstream merge.**
- **The planner builds no parallel plans** (`planner/src/lib.rs`: `assess_parallel = false`). That is why `018_aggregates` fails checks 5, 14 and 16. `scripts/pgvector/tap-accepted.tsv` pins exactly those; one check more or fewer, a test that died, and `ref` mode all still fail. `max_parallel_workers_per_gather`, which the harness pins to 2, is now the width ceiling of a Gravity section.
- **Upstream builds btree indexes in parallel** through the same `table_index_build_scan_parallel` the vector builds use. The merged function keeps the fork's two ERRORs (a relation that isn't the file the scan was initialized for; an MVCC scan with no snapshot). Checked by hand on plain, in-transaction, REINDEX and CONCURRENTLY btree builds.
- **New upstream lints the fork's code must meet:** `lint_alloc`, the thread-local census (`session --lib tls_source_census`), `gravity_lint`. Twelve allocation sites in the vector crates were made fallible; `pgvector_hnsw_graph` reports a refused allocation as `GraphError::HostOutOfMemory`.
- **An auto-merged collision:** both sides had given relcache init-file option tag 12 to a different kind. The fork's tags now count down from 255.
- **pgrust has its own `initdb`.** The harness still creates clusters with C's and sets `PGRUST_PGSHAREDIR`; both still work.
