## 2. What M6 starts from (surveyed 2026-10-20)

**The gate: 8 TAP tests, 37 failing lines.**
- The tests are `003`, `032` and `035` (IVFFlat), and `012`, `020`, `024`, `028` and `045` (HNSW).
- 36 of the lines are `like($stderr, qr/using \d+ parallel workers/)`. That is C's DEBUG1 at `hnswbuild.c:1054` and `ivfbuild.c:961`.
- `045:27` expects `hnsw graph no longer fits into maintenance_work_mem after 0 tuples`, and only C's parallel memory arithmetic produces it:
  - the shared area is `maintenance_work_mem` − 3 MB (`hnswbuild.c:963-970`);
  - so `3073kB` leaves 1024 bytes.
- Recall already passes, because the "parallel" builds currently run serially.

**What pgrust has.**
- **No worker count.** pgrust has no `plan_create_index_workers` and no `amcanbuildparallel`.
  - `index_build` is serial-only and always logs `building index ... serially` (`catalog_index/src/lib.rs:1232-1262`).
  - Reusable pieces:
    - `allpaths::compute_parallel_worker`;
    - `plancat::estimate_rel_size` (`plancat.rs:967`);
    - `Relation::get_parallel_workers` (`rel.rs:244`).
- **Two worker mechanisms exist.** The spike should pick one and record the ruling.
  - **The morsel pool** (`crates/backend/executor/runtime`). The spec picks it (§7.1). B-tree's arm in `nbtsort/src/pool.rs` is the model:
    - it is opt-in (`PGRUST_RUNTIME_INDEXBUILD_POOL`);
    - it excludes CONCURRENTLY;
    - it keeps one leader-owned sort;
    - its gang entry `btbuild_pool_main` (`pool.rs:637`) is only a stub.
  - **The thread-native `parallel` crate** (`CreateParallelContext`, `LaunchParallelWorkers`, …).
    - Shared state is an `Arc`, with no `shm_toc` and no DSM.
    - `vacuumparallel` and parallel query use it.
    - `LookupParallelWorkerFunction` refuses every library except `"postgres"` (`parallel/src/lib.rs:333-346`), so C's `CreateParallelContext("vector", "HnswParallelBuildMain", n)` fails as written.
    - The spec rejected porting C's DSM/bgworker machinery, but this crate already exists and isn't that machinery, so choosing it is a legitimate ruling.
- **Gaps either way.**
  - **Parallel build scans.** The index-build scan cannot join a parallel heap scan: `execindexing/src/build_scan.rs:229-239` passes `None`. tableam's parallel-scan API itself is real (`tableam/src/lib.rs:2201-2261`).
  - **IVFFlat sort.** Shared, coordinated tuplesort is unported, and `Tuplesort` is thread-affine. Hence spec §7.3:
    - workers assign rows to centers;
    - workers stream `(list, tid, value)` to one leader sort;
    - DIVERGENCE: tuple order within a list.
  - **HNSW graph.** The build graph is a plain `Vec<MemElement>` (`pgvector_hnsw_build/src/lib.rs:35-53`) and cannot be shared between threads.
    - Spec §7.2 wants a shared arena of u32 handles, with C's lock set on `pgsync` so loom can test it: `entryLock`, `entryWaitLock`, `allocatorLock`, `flushLock` and one lock per element.
    - The memory accounting is approximate. It is the opt-in bytecmp `spill` case: at 1 MB, C flushes after 1436 tuples and pgrust after 1840. The M1 report assigns it to M6, and `045` needs C's exact parallel arithmetic.
- **Constraints** (spec §7):
  - The kill switch `PGRUST_VECTOR_INDEXBUILD_POOL=0` is on by default.
  - Any refusal falls back to the serial build, and wasm always builds serially.
  - No raw thread spawns: the `lint_determinism` budget must hold.
  - The serial build stays the correctness reference. Parallel builds are nondeterministic, so recall is the check, and bytecmp stays serial and seeded.
- **For the plan to decide:**
  - CREATE INDEX CONCURRENTLY with workers;
  - how to force workers in the gate;
  - how to measure and report build time against C.
