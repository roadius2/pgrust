**Page outline (sections, with the facts to carry).**
- **Title and verdict.** One paragraph from the report's "Read this first": same recall as C PostgreSQL 18.6 + pgvector 0.8.7 at every search setting (within 0.005) and the same index sizes, but slower at almost every vector operation; close to C as a plain PostgreSQL; an hour-long soak with zero errors on both.
- **What was compared.** One node (`borg2`, i9-11900, 61 GiB, Ubuntu 25.04), each server alone in a matched Incus container (six whole cores, 24 GiB), identical settings from one file (`shared_buffers` 8GB, `maintenance_work_mem` 8GB, …), PGDG PostgreSQL 18.6 + pgvector 0.8.7 vs pgrust `main` at `a9c5743a3c` built from source (6 min 19 s), two ann-benchmarks datasets (glove-100-angular 1.18M × 100 as `vector` and `halfvec`; sift-128-euclidean 1M × 128), HNSW m=16/ef_construction=64 and IVFFlat, searches at 1/8/16 clients with recall computed by the client from the datasets' ground truth.
- **Headline tables.** The three `report.py` blocks (glove `vector`, glove `halfvec`, sift `vector`), with the matched-setting rows first and the † threshold marker explained (the "first setting to reach a recall target" rule turns a 0.001 recall difference into a 2× QPS swing; at the same setting the ratio is 0.76×).
- **Benefits (where pgrust is equal or ahead).** Recall identical at every setting; index sizes equal to the MiB; `pgbench -S` 1.10× C at 0.91× the CPU (with the caveat that only 4.8 of 6 cores were busy on both sides, so it may be client-bound); exact-scan throughput 1.06–1.11× at 8 clients on `vector`, and a per-CPU lead there that is confounded (C's parallel-worker start-up, possible JIT); parallel HNSW build memory 0.35–0.40× C's (C reserves the whole 8 GB shared area); stability — 0 failed transactions in the hour, flat windows, no memory growth after the first five minutes; it builds and runs on Linux x86-64 from source.
- **Negatives (where pgrust is behind).** Search QPS at matched settings and 8 clients: 0.72–0.74× (HNSW `vector`), 0.61× (HNSW `halfvec`), 0.76–0.84× (IVFFlat); p99 1.19–1.89×; builds 1.90–2.13× (HNSW `vector` serial), 1.58–1.66× (4 workers), 2.74×/2.19× (`halfvec`), **3.65–4.84× and 2.75–2.97× on IVFFlat (the largest gap)**; inserts under HNSW 0.85–0.95×; DELETE + VACUUM after inserts 1.34–2.84× the time; CPU per search query 1.39–1.64×, per TPC-B transaction 1.38×; memory held higher in every step except the 4-worker builds (1.5–2.4× during searches, 1.74× at the soak peak); exact scan at 1 client 0.47–0.51× (`vector`) and 0.24× (`halfvec`) because pgrust's planner builds no parallel plans while C runs two workers; soak throughput 0.79×; TPC-B-like 0.94×.
- **Why — as leads, not conclusions.** C pgvector's x86-64 kernels are vectorized (AVX/F16C/FMA, `-fassociative-math`) while pgrust keeps C's source-order scalar summation element by element — a deliberate fidelity decision (2026-10-06: no emulation of C's vectorized reductions) that costs more on x86-64 than on the Mac's arm64; pgrust's `halfvec` path on x86-64 has no F16C route (design decision 5); the planner builds no parallel plans (inherited from upstream v0.4-beta); a fixed per-query cost of 0.5–0.7 ms in HNSW search not attributable from this data; `hashbrown::HashMap::insert` in the HNSW build from a Mac profile. None is measured on x86-64 yet.
- **Method and limits** (from the report's Limits): one node; a host shared with two other instances (settle statistics recorded); one run per search point; warm cache; the two contestants ran sequentially, never interleaved; PGDG binary vs source-built pgrust; PG 18.6 baseline while PGDG had 18.7; IVFFlat used 1184 lists on glove this run; memory numbers are container high-water marks (file cache outside); recall ties count as misses (glove has duplicate vectors); `io_method` worker vs sync; no `EXPLAIN` of the exact scan was recorded; OOMScoreAdjust, locale, jit and checksums not equalised or not recorded.
- **Reproduce and evidence.** `scripts/bench/README.md` (site constants and prerequisites), the report's Reproduce section (the full pgrust sha, the exact commands), the fork `https://github.com/roadius2/pgrust`, run id `p1-20261114`, dates 2026-11-14 23:36 → 2026-11-15 13:26 UTC.
